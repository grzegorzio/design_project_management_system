# Описание REST API

Контракт API спроектирован как основа для разработки — фиксирует ресурсы, методы, роли доступа и статусные переходы, вытекающие из бизнес-процесса TO-BE. Полная спецификация — [`openapi.yaml`](openapi.yaml) (OpenAPI 3.0), её можно открыть в [Swagger Editor](https://editor.swagger.io) для интерактивного просмотра.

## Принципы проектирования

- **Ресурсно-ориентированный REST**: `/clients`, `/projects`, `/tasks` — существительные, методы (`GET`/`POST`/`PATCH`) определяют действие
- **Вложенность ресурсов** там, где есть логическая иерархия: `/projects/{projectId}/tasks` — задачи существуют только в контексте проекта
- **Аутентификация через Bearer-токен (JWT)** — единая точка входа `/auth/login`, роль пользователя (`client` / `employee` / `admin`) определяет доступные действия
- **Явные статусные переходы через PATCH**, а не через прямое изменение всех полей — например, `PATCH /tasks/{id}/status` отражает конкретный бизнес-процесс согласования, а не произвольное редактирование записи

## Карта ресурсов

| Ресурс | Методы | Кто может вызывать |
|---|---|---|
| `/auth/login`, `/auth/me` | `POST`, `GET` | Все аутентифицированные роли |
| `/clients` | `GET`, `POST` | Руководитель проекта, администратор |
| `/clients/{id}` | `GET` | Владелец записи (клиент) или сотрудник |
| `/projects` | `GET`, `POST` | Клиент — только свои; Руководитель — все |
| `/projects/{id}` | `GET`, `PATCH` | Руководитель проекта |
| `/projects/{id}/tasks` | `GET`, `POST` | Руководитель, назначенный сотрудник |
| `/tasks/{id}` | `GET` | Клиент (только просмотр), Сотрудник, Арт-директор |
| `/tasks/{id}/status` | `PATCH` | Арт-директор (согласование), Дизайнер (выполнение) |
| `/employees` | `GET` | Руководитель проекта |
| `/employees/{id}/workload` | `GET` | Руководитель проекта |

## Сценарий: согласование макета через API

Соответствует BPMN TO-BE и Use Case диаграмме (`Согласовать макет`, `<<extend>>` → `Отправить на доработку`):

1. Дизайнер выполняет задачу → `PATCH /tasks/{id}/status` `{ "status": "review" }`
2. Арт-директор проверяет макет:
   - если всё в порядке → `PATCH /tasks/{id}/status` `{ "status": "done" }`
   - если нужна доработка → `PATCH /tasks/{id}/status` `{ "status": "in_progress", "comment": "..." }`
3. Клиент видит финальный статус через `GET /projects/{id}` (агрегированный статус проекта складывается из статусов его задач)

## Пример запроса и ответа

**Запрос:**
```http
POST /projects HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{
  "client_id": 12,
  "name": "Ребрендинг сети кофеен",
  "description": "Разработка нового логотипа и фирменного стиля",
  "start_date": "2026-09-01",
  "end_date": "2026-11-15"
}
```

**Ответ:**
```json
{
  "id": 45,
  "client_id": 12,
  "name": "Ребрендинг сети кофеен",
  "description": "Разработка нового логотипа и фирменного стиля",
  "status": "planned",
  "start_date": "2026-09-01",
  "end_date": "2026-11-15",
  "created_at": "2026-08-29T10:15:00Z"
}
```

## Коды ошибок

| Код | Когда возвращается |
|---|---|
| `400` | Невалидное тело запроса (например, отсутствует обязательное поле) |
| `401` | Отсутствует или истёк токен |
| `403` | Роль не имеет прав на действие (например, Клиент пытается вызвать `PATCH /tasks/{id}/status`) |
| `404` | Ресурс не найден |
| `409` | Конфликт состояния (например, попытка перевести задачу из `done` обратно в `todo` напрямую) |

## Связь с моделью данных

Каждый ресурс API соответствует таблице БД — см. [`../er-diagram.png`](../er-diagram.png) и [`../../db/schema.sql`](../../db/schema.sql). Поля в схемах `openapi.yaml` намеренно зеркалят колонки таблиц `clients`, `projects`, `tasks`, `employees`, чтобы контракт API и модель данных не расходились.
